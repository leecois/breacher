# Architecture

This document maps the code and records why the reader and the solver work the way they do. The
code carries only short notes; the reasoning lives here.

## Bird's-eye view

A frame of the game goes in; a route comes out, or a refusal with a reason.

```
frame (pixels) ──► reader ──► reading ──► planner ──► plan ──► window, overlay, terminal
                     │           │           │
                     │           │           └─ solver: exact search over legal picks
                     │           └─ matrix, sequences, buffer size, geometry, quality
                     └─ rejects a frame it cannot read with confidence
```

Everything that decides the answer is in one crate, `breach-core`, which has no platform code. The
other crates and the app only feed it pixels and show what it returns.

## The reader

The design goal is zero wrong answers, at the price of some refusals. Every stage either produces
something it can stand behind or stops with a `Stage` that says where reading failed.

### 1. Strokes

The reader works on V = max(R, G, B). Interface text is bright and saturated, so V separates it from
the backdrop whatever its hue and survives tone shifts better than luma. The plane is max-pooled,
which keeps thin bright strokes that averaging would lose.

A white top-hat removes everything that is not a thin bright stroke: header bars, banners and
filled panels go to zero. The threshold is relative to the frame's own brightest strokes, so no
absolute colour or brightness is assumed. This is what makes over-bright HDR captures and gamma
shifts mostly harmless.

### 2. The matrix

The code matrix is the only thing searched for blindly: it is the largest regular grid of
code-sized marks. Its pitch is measured separately in x and y, so stretched frames work, and it
becomes the unit for everything else.

Cell occupancy is judged against the matrix's own stroke level, not the frame's, because on soft
frames the thin code strokes are much fainter than the large headings.

Two repairs guard against a matrix that is found too small. A block that is not square has lost a
row or a column, so its short side grows over lines whose cells hold glyph-shaped strokes. A square
block can still have lost a row and a column together, so any side whose neighbouring line holds
code-sized strokes in most cells is taken in as well. Legal text, decorative tables and borders are
not code-sized, so they cannot extend the matrix. Missing cells inside the matrix mean the breach
has started or something covers it, and the frame is rejected.

### 3. The sequence list

Nothing here relies on a fixed position. The search region starts just right of the last matrix
column. Long horizontal rules cut it into bands, and the list is the band whose first column holds
the most rows of codes; on a tie the lower band wins, because a panel's title sits above its list.

Column 0 is the leftmost column of codes in the band. Locking onto column 1 instead would silently
drop every first code, so the column is found from structure: every sequence has at least two
codes, and one pitch to the left of column 0 there is nothing. A mask of glyph-sized pieces locates
the column, but whether a slot holds a code is judged on the full mask, since on soft frames a
character can break into pieces smaller than the size filter.

When the rule under the panel title is too faint to separate the bands, the title lands in the
list's band. It sits less than a row above the first sequence, and two sequences are never that
close, so of two runs closer than the smallest row pitch the upper one is dropped. A bright filled
row is the banner of a daemon that is already installed.

### 4. The buffer

The buffer panel is the lowest box above the sequence list whose two border lines pass over slot 0,
sit about one row apart and end at the same place. Its width gives the buffer size. A side border
found on its own counts only if a horizontal border line runs up to it and stops there. Counting
the dashed slots can only under-count, so it serves as a veto and as the last resort.

If only the buffer cannot be read, the caller may supply a size to assume
(`ReadOptions::buffer_fallback`), and the result says the value was assumed.

The layout constants measured on captures (`Layout`) are used only to report how far a screen is
from the usual layout (`Quality::layout_fallback`).

### 5. Codes

The game draws every code from six two-character tokens in one font, so within a frame all
instances of a token are near-identical. Recognition therefore works per frame:

1. Each crop is normalised to a 32×24 feature. Strokes touching the window edge belong to a
   neighbour and are dropped. A soft binarisation makes the feature follow where the strokes are,
   not the tone curve or the background behind the code.
2. Crops are grouped into fragments by mutual similarity, with no reference to templates. The
   threshold sits above the highest similarity seen between two different tokens, so a fragment is
   one token.
3. Fragments are assigned tokens to maximise template evidence, with one structural rule: two
   fragments that look different cannot share a token.

Sequence codes get a small bonus for tokens the matrix contains. It settles near-ties without
forcing a label; a hard restriction would silently turn a code the matrix lacks into its nearest
look-alike. Where no template covers a token, the matrix's own fragments stand in as evidence.

### 6. The gate

A frame is accepted only if every code passes a confidence gate (`glyph::Gate`): enough template
evidence, consistency within its fragment, margin over the next token and separation from other
fragments. A crop that belongs to no fragment, such as a cell under the cursor, fails the gate
instead of being read as something.

### Scale and speed

The interface scale is not known in advance, so a few scale priors are tried in order. Layout runs
on a plane pooled to a pitch of about 28 px. On large frames everything after the layout works on a
frame pooled to a pitch of at least 56 px, which keeps all the shape a code needs.

## The solver

The rules encoded in `solver`: the first pick comes from the top row, each following pick
alternates between the column and the row of the previous one, a cell is picked once, and at most
`buffer` picks are made. A daemon uploads when the buffer matches its sequence and then stays
uploaded.

The search is depth-first branch and bound. The bound is the best reward any string of the
remaining length could still earn, ignoring the matrix: a dynamic program over the product of the
daemons' matching automata. It accounts for overlaps and conflicts between daemons, and it stays
admissible for every matching rule because each of them requires the sequence to occur in the
buffer. The objective is the highest total weight, then the fewest picks. A node budget bounds the
search; `Solution::proven` says whether it finished.

What the game does to a daemon's progress on a wrong pick is not confirmed, so the matching rule is
a parameter (`Matcher`): `Substring`, `Retest`, `Strict`, and `Unanimous`, which requires all three.
`solve_robust` returns a route that holds under every rule and, separately, a better one that
depends on plain substring matching when there is one. `rule_probe` finds a route whose outcome
tells the rules apart. `verify` replays a route independently and is run before anything is shown.

## The planner

`plan` turns a reading into a route with screen positions for each pick. It applies the player's
choices without reading the frame again: which daemons are wanted, a buffer size set by hand, and
whether more daemons or the last daemon comes first (`Priority`).

`plan_from` plans the rest of a breach that is under way, from the picks already made. `rule_check`
returns a route whose result differs between the wrong-pick rules still in play, with what each
outcome then says about the rule; a rule that has been ruled out narrows both the check and the
routes planned afterwards.

## Learning the rule

`reader::buffer_codes` reads the codes standing in the buffer of a screen whose reading is known,
with the same templates and the same gate as the reader; a slot that flashes is neither a code nor
empty, and then nothing is read. `Followed::learn` holds the daemons the game installed against
`solver::uploaded_by` for each rule still in play and returns the rules that fit, or says that
none does. Both front ends call it on the screen that follows a breach, once the buffer has read
the same twice.

## Front ends

- **WebAssembly.** `bp_read`, `bp_plan`, `bp_check`, `bp_follow` and `bp_learn` take bytes and return a
  little-endian `u32` length followed by JSON. `bp_follow` keeps no state: the page hands it the
  breach as it stood at the last look and gets it back as it stands now. The module is built with SIMD so the reader's filters vectorise.
- **Page.** Decodes dropped or pasted images with the browser, calls the module, and draws the
  result. It works without the shell. In a browser it can also be shown the game by screen
  sharing. Five times a second it shrinks the shared picture to a few hundred brightness values;
  when the picture has changed since the last attempt and come to rest, the full frame is read,
  and a frame that is no breach is passed over in silence. A breach that was read is then
  followed with `bp_follow` at the same pace, which costs about a hundredth of a second a look at
  2560×1440. The beat comes from a worker and the frames from the track itself where the browser
  offers that, because a page covered by the game gets neither timers nor repaints at full rate.
- **Desktop shell.** On the hotkey it captures the game window, reads it natively, sends the answer
  to the main window and the route to the overlay. The overlay is a transparent, click-through
  window that never takes focus. While a route is up the shell looks at the game window again
  every 0.4 seconds and takes the route down as soon as the game has settled every daemon, once
  the matrix has been gone for four looks in a row, or when the game is minimised. Where a repeated capture would flash a border round
  the game, as on Windows 10, the route stays up for a fixed time. A capture that is not read
  puts a short notice on the same overlay, since nothing else reaches a player inside the game.
  The overlay is put back above the other windows at every capture and every look: a game that
  keeps itself on top covers it again each time it comes to the front. Asked to, the shell also
  watches the game while it is in front: it glances at the window every 0.6 seconds, reads the
  frame when the picture has changed, and draws the route once two reads in a row agree, so that
  a screen still opening is not taken at its word.
  The same looks are read for picks. `progress::look` tells, by colour alone, which cells show
  their code, the pointer's box, the flash of a pick or the brackets left by one, and how many
  buffer slots are filled for good; the code previewed under the pointer does not count. It also
  reads the green and red bars the game lays over daemons it has installed or failed.
  `progress::advance` puts newly picked cells into the only order the rules allow, and refuses a
  look that does not fit. The shell then counts the picks off the route, or plans the rest again
  with `plan_from` when a pick left it. A look that is refused changes nothing. A watched folder reads new screenshots as they appear and needs no
  capture permission. The shell writes a settings file and a plain-text log beside it. It runs as
  a single instance. Closing the main window puts it away and leaves the program in the tray, hotkey
  and all; the tray menu ends it. Where there is no tray, or the player turns that off, closing the
  window ends the program, which also releases the hotkey. When the
  system refuses the wanted combination, the next free default is bound and the window says so.
  At start it reads `latest.json` from the latest full release; a newer version is installed only
  on the player's say and only if its signature, which names the version, verifies.
- **Command line.** The same `read_and_plan` call, printed as text.

## Invariants

- The reader returns an exact reading or a refusal. A change that reduces refusals must not add a
  single wrong reading in the sweep.
- `breach-core` contains no platform code and builds for `wasm32-unknown-unknown`.
- Nothing in the project opens a network connection.
- Fixed layout offsets are never used to locate anything, only to report.
- A route is replayed by `verify` before it is displayed.

## Tests

- Unit tests in each module; the solver is checked against exhaustive enumeration under every
  matching rule.
- `crates/breach-core/tests/corpus.rs` reads every labelled capture exactly, checks the rejections,
  and checks that degraded copies are read exactly or refused.
- `crates/breach-core/tests/synthetic.rs` composes screens the corpus does not contain.
- `breach eval corpus/cpah --loo --full` runs the perturbation sweep with templates learned without
  the capture under test. It is the measure to quote when the reader changes.
